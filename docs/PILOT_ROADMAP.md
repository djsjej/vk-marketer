# План разработки пилотной версии Рекламной Организации Vizit

**Дата:** 15.05.2026
**Парный документ:** `CONSTITUTION_v2.md` (архитектура и иерархия)

## Назначение документа

Пошаговый roadmap от текущего состояния (Phase 6 — Боба разговаривает)
до **полноценной пилотной версии** где Боба сам управляет всей командой
и автоматически проводит рекламные циклы.

Загружай этот файл в новый Claude-чат вместе с `CONSTITUTION_v2.md`
чтобы продолжать работу без потери контекста.

---

## Определение пилотной версии

**Пилотная версия** = MVP который Vizit может реально использовать для
своих рекламных кампаний без участия разработчика в каждом цикле.

**Минимальный набор:**
1. ✅ Vizit пишет Бобе через Telegram
2. ✅ Боба понимает контекст ниши и даёт стратегию
3. ❌ Боба сам вызывает функции парсинга/анализа когда нужно (Phase 7)
4. ❌ Боба может делегировать подзадачи специалистам команды (Phase 8)
5. ❌ Результаты тестов накапливаются в базе знаний (Phase 9)
6. ❌ Один полный цикл проходит от задачи до отчёта без вмешательства (Phase 10)

Пилотная версия = Phase 7 + 8 + 9 + 10. Это ~12-15 часов чистого
кода + тесты + интеграция.

## Phase 7 — Tool Use у Бобы

**Цель:** Боба сам вызывает наши функции через Anthropic Tool Use API.

**Что Боба получает в инструменты:**
- `get_account_status()` — возвращает баланс, активные кампании
- `parse_orthodox_audience(max_per_group)` — запускает наш vk_audience
- `find_intersections(groups, min_groups)` — пересечения
- `get_recent_campaign_stats(campaign_id)` — статистика кампании
- `search_community(query, limit)` — поиск сообществ
  (когда будет PKCE — реальный VK API, пока stub)
- `read_knowledge_base(topic)` — чтение из базы знаний
  (когда она появится в Phase 9)

**Как это будет работать с точки зрения Vizit'а:**

> Vizit: «Боба, собери горячую аудиторию»
> Боба: «Принял. Запускаю парсинг 4 проверенных сообществ...»
> [Боба вызывает parse_orthodox_audience() через tool]
> Боба: «Готово. Собрал 17 656 уникальных, из них 1 942 в 2+ группах.
> Загружать в VK Ads?»
> Vizit: «Да»
> Боба: [вызывает create_remarketing_users_list()]
> Боба: «Загружено. ID списка 2500123. Положи в Railway env
> VK_AUDIENCE_SEGMENT_IDS чтобы я мог использовать в кампаниях.»

**Технически:**
- Используем Anthropic Tool Use (поле `tools` в API запросе)
- Каждый tool — Python функция с JSON schema аргументов
- Когда Claude в ответе использует tool — обрабатываем, выполняем,
  возвращаем результат, продолжаем диалог
- История диалога включает tool_use и tool_result блоки

**Файлы:**
- Новый `src/agents/boba_tools.py` — определения tools и их обработчики
- Расширение `src/agents/dialog.py` — поддержка tool use loop
- Модификация `_boba_chat_turn` в `handlers.py`

**Тесты:**
- Каждый tool отдельно
- Полный цикл: запрос → tool call → результат → продолжение диалога
- Обработка ошибок tools (что если функция упала)

**Оценка:** 2-3 часа кода + 30 минут тестов

## Phase 8 — Подчинённые как агенты

**Цель:** Боба может делегировать подзадачи Рите, Кириллу, Тимуру, Алине.

**Архитектурный выбор (по решению Vizit'а от 15.05):**

**Вариант А (выбран):** Подчинённые как **внутренние диалоги Бобы**.
Когда Боба делегирует — он внутренне создаёт DialogAgent с персоной
подчинённого, ведёт с ним короткий диалог, возвращает результат
обратно во внешний диалог с Vizit'ом.

Преимущества: одно меню для Vizit'а, простая архитектура.
Недостатки: подчинённые не помнят прошлые задачи между делегациями.

**Вариант B (отложен):** Каждый подчинённый — отдельный командный
режим (`/rita`, `/kirill` и т.д.). Vizit может говорить напрямую.

**Реализация Варианта А:**

Боба получает новый tool — `delegate_to(specialist, task)`:
- `specialist` = «rita» | «kirill» | «timur» | «alina»
- `task` — формализованное ТЗ

Tool implementation:
```python
async def delegate_to(specialist: str, task: str) -> str:
    persona_map = {
        "rita": RITA_PERSONA,
        "kirill": KIRILL_PERSONA,
        "timur": TIMUR_PERSONA,
        "alina": ALINA_PERSONA,
    }
    persona = persona_map[specialist]
    sub_agent = DialogAgent(persona=persona)
    response = await sub_agent.chat(user_message=task)
    return response.text
```

Каждый подчинённый получает свой набор tools:
- Рита: парсинг, пересечения, фильтр, выгрузка
- Кирилл: Claude API для генерации текстов и описаний баннеров
- Тимур: VK Ads API для запуска и управления кампаниями
- Алина: чтение статистики, запись в базу знаний

**Оценка:** 3-4 часа кода + 1 час тестов

## Phase 9 — База знаний

**Цель:** Накопление опыта между циклами.

**Выбор технологии:** Markdown файлы в `docs/knowledge_base/`.
Преимущества:
- Vizit может читать и редактировать руками
- Не требует БД-миграций
- Версионируется через git
- Алина может писать через простую запись в файл

Недостатки:
- Поиск медленнее чем по индексу БД
- Структура зависит от дисциплины записи

При росте — мигрируем в PostgreSQL (у нас уже есть `src/db/` для
других данных).

**Структура папки:**
```
docs/knowledge_base/
├── README.md              # индекс всего что есть
├── working_combos.md      # рабочие связки сегмент+креатив
├── failed_combos.md       # провальные связки и причины
├── segment_rankings.md    # топ-сегменты по CPL
├── creative_rankings.md   # топ-креативы
├── vk_moderation_log.md   # что забанили и за что
├── current_hypotheses.md  # текущие на тестировании
└── orthodox_calendar.md   # православные события (для сезонности)
```

**Tools для агентов:**
- `read_knowledge(file)` — чтение раздела
- `append_knowledge(file, entry)` — добавление записи (только Алина)
- `search_knowledge(query)` — поиск по всем файлам

**Шаблон записи (для воспроизводимости):**
```markdown
## Связка: Подписчики Постной Трапезы × Молитвенный призыв
**Период:** 2026-05-20 — 2026-05-27
**Бюджет:** 3500₽
**Метрики:** CTR 1.2%, CPC 18₽, CPL 32₽
**Конверсий:** 109 подписчиков, 18 имен для поминовения
**Вывод:** Работает. Масштабировать в 3 раза.
**Связь:** /audience/seg_42, /creative/cr_119
```

**Оценка:** 2-3 часа кода + 30 минут тестов

## Phase 10 — Полный автоматизированный цикл

**Цель:** Vizit ставит задачу, через 10 дней получает отчёт. Между
этими событиями — никакого ручного участия разработчика.

**Что нужно реализовать:**

1. **Сценарный движок** — Боба знает стандартный цикл и ведёт его шаг
   за шагом. После каждого шага — пишет Vizit'у статус-апдейт.

2. **Background tasks** — некоторые шаги длительные (тесты идут 3-5
   дней). Боба не сидит в диалоге всё это время, а планирует через
   APScheduler (у нас уже есть `src/scheduler/`).

3. **Триггеры алёртов** — если что-то пошло не так (бан кампании,
   слишком быстрый расход), Боба сам пишет Vizit'у.

**Пример полного цикла:**

```
День 0, утро:
  Vizit: «Боба, давай провести цикл под привлечение к Радонице»
  Боба: декомпозирует, предлагает 3 стратегии
  Vizit: «Беру вторую»
  Боба: создаёт scheduler-задачи на 10 дней вперёд

День 0, обед:
  Боба → Рита: «Спарси 20 сегментов под радоницу»
  Рита возвращает таблицу сегментов
  Боба → Vizit: «Рита подобрала 20 сегментов. Топ-5: ...»

День 1:
  Боба → Кирилл: «Сделай креативы на топ-5 сегментов»
  Кирилл генерирует 5×3=15 связок на каждый
  Боба → Vizit: «Креативы готовы, утверждать?»
  Vizit: «Да»

День 2:
  Боба → Тимур: «Запускай»
  Тимур создаёт кампании в VK Ads
  Боба → Vizit: «Запустили 75 связок, бюджет 37500₽ на тесты»

Дни 3-7:
  Тимур через scheduler проверяет связки каждые 6 часов
  Связки которые не работают — отключаются по правилам
  Если что-то идёт не так — алёрт Vizit'у

День 8:
  Боба → Алина: «Анализируй»
  Алина считает метрики, пишет в базу знаний, готовит отчёт
  Боба → Vizit: «Итоги цикла: потрачено X, привлечено Y, CPL Z.
  Топ-3 связки... Следующий цикл предлагаю...»
```

**Оценка:** 4-6 часов кода + 2 часа тестов + 2 часа интеграции

## Phase 11 — Обработка фото

**Цель:** Перед публикацией бот мягко улучшает фото по правилам VK Ads.

**По правилам VK Ads (проверено 15.05.2026):**
- Без агрессивной цветокоррекции
- Без перенасыщенных фильтров
- Без эмодзи и спецсимволов на изображении
- Текст ≤20% площади (если есть)
- Без склейки нескольких изображений

**Реализация:**
- PIL/Pillow для базовой обработки
- Auto-contrast по гистограмме (мягкий, не агрессивный)
- Лёгкий sharpening (USM с малым радиусом)
- Denoising если изображение шумное
- Проверка через Claude Vision: есть ли проблемы для модерации
  (процент текста, наличие проблемных элементов)

**Опционально:**
- Если на фото есть текст ≥ 20% — предупреждение Vizit'у до отправки
- Если изображение низкого качества (< 1080p) — предложение апскейла
  через ESRGAN или другую ML модель

**Оценка:** 1.5-2 часа кода + 30 минут тестов + полчаса проверки
на реальных фото

## Phase 12 — PKCE flow для user-token

**Цель:** Получить user-token VK ID чтобы использовать `groups.search`
(сейчас service-token даёт ошибку 1051) и `likes.getList` (для анализа
активности).

**Что это даст организации:**
- Рита может сама искать новые правосл. сообщества по ключу
  («православие», «монастырь», «икона»)
- Возможность анализировать активность через `likes.getList` — кто
  реально комментирует и лайкает посты pomolimsy
- Лучшая look-alike качества (больше входных данных)

**Технически:**
- OAuth Authorization Code Flow с PKCE
- Серверный обработчик OAuth callback (новый endpoint в Telegram-боте)
- Хранение refresh_token в PostgreSQL
- Авторефреш access_token когда истекает
- Vizit один раз авторизуется через VK ID, дальше работает автоматом

**Файлы:**
- Новый `src/vk_user_auth/` модуль (по аналогии с `src/vk_ads/auth.py`)
- Расширение `VKAPIClient` чтобы переключаться между service token
  (для публичных методов) и user token (для расширенных)
- Миграция БД для хранения токенов

**Оценка:** 2-3 часа кода + 1 час тестов + полчаса OAuth-настройки в VK

## Phase 13 — Автоматизация через cron

**Цель:** Триггеры по календарю и регулярные задачи без ручного запуска.

**Cron-задачи:**
- Еженедельный отчёт от Алины (понедельник, 10:00) — итоги недели,
  топ-3 связки, рекомендации Бобе
- Месячный рейтинг сегментов и креативов (1-е число, 10:00)
- Триггеры перед православными праздниками — за 5 дней Боба пишет
  Vizit'у «приближается Радоница, давай готовить цикл»

**Православный календарь (вручную составляется в Phase 9):**
- Радоница (вторник 9-го дня после Пасхи) — пиковый день поминовения
- Дмитриевская родительская суббота (ноябрь)
- Великие посты — пик активности правосл. аудитории
- Рождественский пост, Великий пост, Петров пост, Успенский пост
- Дни поминовения святых актуальных pomolimsy

**Технически:** Расширение существующего `src/scheduler/` (APScheduler
у нас уже работает для других задач).

**Оценка:** 2-3 часа кода + 1 час тестов

## Порядок реализации (рекомендация)

**Сессия 1 (~3 часа):** Phase 7 — Tool use у Бобы. Это критическое
звено, всё остальное упирается в него. Без tool use Боба только
советует, действий не делает.

**Сессия 2 (~3 часа):** Phase 9 — База знаний (markdown). Делаем
до Phase 8 потому что подчинённым она нужна сразу (Алина пишет туда,
Боба читает).

**Сессия 3 (~4 часа):** Phase 8 — Подчинённые как агенты. Боба
получает tools для делегирования.

**Сессия 4-5 (~6 часов):** Phase 10 — Автоцикл. Сценарный движок,
background tasks через scheduler.

**Сессия 6 (~2 часа):** Phase 11 — Обработка фото. Можно вставить
раньше если Vizit будет много загружать фото и они будут отклоняться
модерацией.

**Сессия 7 (~3 часа):** Phase 12 — PKCE flow. Снимает технические
ограничения, позволяет автопоиск групп.

**Сессия 8 (~3 часа):** Phase 13 — Cron-автоматизация. Финальный
полировочный слой.

## Метрики успеха пилотной версии

После Phase 10 пилотная версия считается работающей если:

1. ✅ Один полный цикл от задачи Vizit'а до отчёта проходит без
   ручного вмешательства разработчика
2. ✅ CPL подписчика в православной нише ≤ 50₽
3. ✅ База знаний накопила минимум 10 рабочих и 5 провальных связок
4. ✅ Vizit может вернуться через неделю и Боба помнит контекст
   предыдущих циклов
5. ✅ Хотя бы один сегмент масштабирован после успешного теста

После выхода на эти метрики — добавляем Phase 11-13 и
оптимизируем под реальные узкие места которые будут видны.
